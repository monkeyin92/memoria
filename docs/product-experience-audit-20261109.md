本次审计从信息架构、用户流程、操作效率、反馈机制、视觉层级、组件一致性六个维度，走查了微信小程序、设备配网链路和已有硬件验收证据。最终判断标准是用户能否理解当前状态、知道下一步、在失败后恢复，以及系统是否诚实表达已经完成的事情。

## 结论

小程序当前本地行为回归已通过 660 项，视觉 harness 在 320/375/390/430 宽度、1.3 倍字体下完成 180 个布局检查；这证明最新代码在测试夹具和静态布局范围内稳定。它不等于微信线上版本、控制 API 网关、真实 BLE/Wi-Fi、真实设备屏幕或刷机结果已经验收。当前工作区仍有固件、R02、文档和备份脏改动，审计过程保留了这些改动。

本轮已落地的三个 P1 根因修复是：安全提醒读取失败不再伪装成空数据；长期记忆纠正可以编辑并只提交新文本；设备在线状态使用 live runtime 连接证据，配网页面后台恢复时会清除失效的 busy/network 状态并重新观察。剩余风险集中在监护人数据主体一致性、登录会话恢复、硬件休眠与收音反馈，以及多个跨页面状态和文案契约。

## P1：当前必须继续处理

### 1. 监护人看到的对象与计数必须一致

监护人首页同一张卡展示孩子的近期摘要，却仍按家长自己的 session 计算“今天聊天次数”，会出现孩子有对话而首页显示 0 次。进入“回顾”后，已有的孩子摘要也不能沿首页入口连续看到。实现应让首页和回顾共用孩子 days/summary 数据源，加载失败时显示未知或同步失败，不能伪造 0；整个链路必须继续遵守 guardian capability、auth epoch 和不展示原话/录音的边界。

状态：已交实现 Agent，等待结果和独立验证。

验收：同一 guardian fixture 在首页和回顾显示同一个孩子主体；有数据时计数和摘要一致；数据失败时不显示 0；self-use 路径回归不变。

### 2. 登录失效必须可恢复

当前多个页面在用户拒绝登录、会话清除或请求返回 401 后只留下“请先登录”或加载状态，没有明确 CTA；绑定页尤其容易停在“正在读取机器人启用信息”。此外，现有短期 access session 没有已证实的续期路径。登录续期涉及 token 存储、微信 session 生命周期、账号切换和隐私边界，不能只把长期凭证写进小程序 storage。

状态：外部研究 Agent 因 provider 认证失败，已由当前 checkout 完成只读契约核验。Control API 已有 `/v1/auth/refresh`、短期 900 秒 access token、最长 30 天的 HttpOnly/SameSite=Strict refresh cookie、服务端 hash 存储和 rotation/replay revoke；小程序客户端没有调用 `/refresh`，也没有 refresh 状态机。客户端现在只把 access token 和过期时间写入 storage，收到 401 后立即清空账号和设备上下文。因此这是“后端已接通、客户端未接通、真实微信 cookie 链路未验证”。

推荐方案是保留 refresh token 在 HttpOnly cookie，客户端只在同一认证 epoch 内对 401 做一次串行 refresh，再重放原请求；refresh 401 才清空账号，refresh 409 按 `Retry-After` 做一次受控重试。并发请求共用一个 refresh promise，旧账号切换或 logout 时使其失效。禁止把 refresh token 放入小程序 storage。上线前必须验证微信客户端是否会保存并回传该 cookie、网关是否保留 `Set-Cookie` 和 path、跨冷启动/后台恢复是否可用，并完成 rotation、replay、logout-all、账号切换和旧响应不回填测试。

状态：页面 CTA 和失效回退列入下一实现批次；续期实现等待后端、安全和产品确认上述 cookie 链路与并发语义。

验收：每个受保护页面都有可达的“去登录/重新登录”；401 后旧请求不能回填新账号私密数据；续期失败回到登录而不是死循环；真实控制 API 和微信登录链路需单独验收。

### 3. 硬件在黑屏、休眠和收音切换时要告诉用户发生了什么

已有真实设备证据显示：深睡唤醒约 16.7 秒且需要两次点击；唤醒到麦克风可用约 3.4 秒，首句可能被吞；安静时段点击后没有可见或可听反馈；二维码刷新提示被二维码层遮住；激活错误页显示白屏和原始 ESP/HTTP 错误码。这些问题会让用户把“正在连接/安静时段/网络错误”误判成设备损坏。

状态：代码证据和既有真机验收已确认，当前轮没有刷机或打开串口；列为硬件 P1 修复批次。

验收：深睡唤醒有单次可理解的反馈和明确完成态；麦克风 ready 前保持唤醒提示，首句不丢；安静时段显示短暂状态；二维码刷新提示在二维码层上方可见；错误页只显示用户可行动的说明和短支持码，并阻止错误页上的二维码误触。

### 4. 小程序、固件和真实操作模型要一致

扫描步骤已修复为“扫描机器人屏幕上的二维码”的方向；仍需统一完成页“灯亮起来”、点屏唤醒、离线故事和真实固件菜单之间的契约。当前硬件证据显示离线故事入口关闭，而小程序仍宣传“离线故事”。在功能启用前，入口和承诺必须同步关闭或明确标注不可用。

状态：文案部分待下一批次，硬件契约待真机复验。

## 硬件 P2/P3 队列

先完成 P1 的状态反馈，再处理硬件体验细节：提高 listen/think/sleepy 在曲面屏上的对比度；显示充电和低电量状态；保留用户设置的亮度而不是每次唤醒重置为 80；移除或修复离线菜单在主循环中的阻塞延时；清理不可达 wake-word drawer 和与圆形点阵屏不匹配的 `device-screen` 插画。硬件修复必须以同一固件构建的真实设备照片、串口时序和回归日志验收，host preview、静态测试和编译通过不能替代屏幕验收。

## 六个维度的共性原则

1. **信息架构**：首页展示状态、近期回顾和安全提醒；设备管理承载绑定、网络和诊断；监护人页面只展示授权范围内的孩子摘要。避免同一能力分散在 profile、memory-lifecycle、child-memory 和 guardian 多个入口却使用不同名称。
2. **用户流程**：任何等待、后台恢复、登录失效、设备离线和取消都要有下一步；不能让用户靠返回箭头逃离 spinner 或靠猜测决定是否重扫。
3. **操作效率**：保存动作要合并连续修改，错误要保留输入，二维码刷新和重新读取要有单点恢复入口；每次 tab show 不应无条件触发整页十余次请求。
4. **反馈机制**：区分成功、空数据、无法读取、确认离线、历史 ACK 和设备已激活；错误码只用于日志，用户看到行动说明和短支持码。
5. **视觉层级**：错误、待确认、离线和成功的颜色、文案、图形要一致；黑屏设备应有可识别的睡眠/连接反馈；所有主要操作保持足够点击区域。
6. **组件一致性**：登录 CTA、重试按钮、状态 pill、确认 sheet、设备插画和返回按钮应复用同一套组件与 tokens，减少页面各自定义相反语义。
